# 01 · 架构总览

> 本文是后端 FastAPI 实现的施工图。前端已按本架构的 API 契约与数据模型对齐（见 `frontend/src/types` 与 `frontend/src/api`）。

## 1. 需求解构（量化目标）

| 维度 | 目标 | 说明 |
| --- | --- | --- |
| 租户规模 | 100+ 租户，单租户 1k~10k 内容 | 多租户隔离是核心 |
| 内容规模 | 单租户百万级文章 | 需索引 + 分区预留 |
| 读写比例 | 读多写少（约 9:1） | 引入 Redis 缓存读热点 |
| 并发峰值 | 500 QPS（读），50 QPS（写） | FastAPI 异步 + 连接池可满足 |
| 一致性要求 | 内容最终一致，审核/版本强一致 | 事务覆盖写链路 |
| 实时性 | 审核通知近实时（秒级） | Celery 异步任务 |
| 可用性 | 99.9%（月宕机 < 43 分钟） | 单区部署 + 主备数据库即可 |

## 2. 技术栈与选型理由

| 组件 | 选择 | 理由 |
| --- | --- | --- |
| Web 框架 | FastAPI | 原生 asyncio、自动 OpenAPI 文档、Pydantic 校验一体 |
| 数据校验 | Pydantic v2 | 类型安全、请求/响应模型统一、性能高 |
| ORM | SQLAlchemy 2.0（asyncio） | 成熟的 async ORM，配合 asyncpg 驱动 |
| 数据库 | PostgreSQL 16 | JSONB、分区表、行级锁、事务强 |
| 缓存/锁 | Redis 7 | 缓存三件套、分布式锁、Celery broker |
| 异步任务 | Celery + Redis | 异步任务、定时调度（beat）、重试、延迟执行 |
| 迁移 | Alembic | SQLAlchemy 官方迁移工具 |
| 认证 | JWT（python-jose/pyjwt） | access + refresh 轮换 |
| 对象存储 | 本地磁盘 + 抽象层 | 学习阶段本地落盘，接口预留 OSS/S3 |
| 部署 | Uvicorn（ASGI）+ Gunicorn | 异步网关，支持多 worker |

## 4. 分层与请求生命周期

```
HTTP 请求
  → 中间件（traceId、日志）
  → 依赖注入：get_current_user（JWT 校验）
  → 依赖注入：get_current_tenant（X-Tenant-Id 校验）
  → 依赖注入：require_permission（权限码校验）
  → 路由函数（Pydantic 自动校验入参）
  → Service（业务逻辑，事务边界）
  → SQLAlchemy AsyncSession（多租户过滤）
  → 响应包装（统一 { code, message, data }）
```

FastAPI 中「守卫」对应「依赖注入」：`Depends(get_current_user)`、`Depends(require_permission("content:write"))`。

## 6. 演进路线（学习路径 = 扩容路径）

| 阶段 | 触发条件 | 动作 |
| --- | --- | --- |
| 单体 | 当前 | 单应用 + 独立 Celery worker |
| 读写分离 | 读 QPS > 2000 | PostgreSQL 只读副本 + 读路由 |
| 缓存层 | 热点内容 | Redis 缓存详情/列表 |
| 独立 worker | 任务量增大 | Celery 多 worker / 多队列 |
| 分库分表 | 单租户内容破千万 | 按 tenantId 分片或分区表 |

> 建议：先把单体做扎实，理解每个模块的边界与事务边界，再谈拆分。
