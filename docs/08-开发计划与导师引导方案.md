## 2. 架构决策与对既有文档的修正

### 2.1 分层与请求生命周期（同 docs/01）

```
中间件（traceId / 日志 / CORS）
  → 依赖注入（get_current_user → get_current_tenant → require_permission）
  → 路由层（薄：Pydantic 校验 + 编排）
  → 服务层（厚：业务逻辑、事务边界、状态机）
  → 数据层（SQLAlchemy 2.0 async + Alembic）
```

核心纪律：**路由层不碰事务，服务层持有事务边界**；`async with db.begin()` 收敛在 Service。

### 2.2 关键权衡（已在会话中确认）

| 决策点 | 方案 | 放弃了什么 / 如何补偿 |
| --- | --- | --- |
| 多租户隔离 | 应用层 `with_loader_criteria` 全局注入 `tenant_id` 过滤 | 放弃 PG RLS 数据库级兜底 → 用「跨租户越权」集成测试补偿 |
| 乐观锁 | `Content.version` 兼任版本号 + 乐观锁，`rowcount==0` → 409 | 客户端需处理 409 刷新重试 |
| JWT | access 15min 无状态；refresh 落库存 hash、可吊销、轮换 | refresh 多一次 DB 查询；并发刷新需防重 |
| 序列化 | `CamelModel` 基类（`alias_generator=to_camel`） | 模型 snake_case 与 API camelCase 的映射心智负担 |
| 删除 | 业务表软删除（`deleted_at`）+ 查询默认过滤 | 所有查询需带过滤（由全局注入根治） |
| Celery broker | Redis（docs/05 结论） | RabbitMQ 的消息可靠性；compose 中 rabbitmq 服务可移除 |

### 2.3 对 docs 的 4 项生产级修正（实施时执行）

1. **密码哈希**：Python 3.13 下 `passlib` 与新版 `bcrypt` 不兼容 → 改用 `pwdlib[argon2]`（passlib 的现代替代，API 相近）。
2. **时间**：`datetime.utcnow()` 已弃用 → 统一 `datetime.now(timezone.utc)`；全链路统一 aware datetime，禁止 naive/aware 混用。
3. **JWT 库**：`python-jose` 维护停滞 → 改用 `PyJWT`（`jwt.encode` / `jwt.decode` API 等价）。
4. **Alembic**：首次建表可用 autogenerate；后续演进须人工审阅迁移脚本（autogenerate 检不出 `server_default` 等差异），迁移文件入 git。

## 4. 协作流程（导师模式）

每个子任务的标准循环：

1. **引导包**：目标与边界（做什么/不做什么）、实现顺序、关键提示（含最小示例片段）、自查清单
2. **你实现**：亲手敲码；卡住贴报错全文 + 已尝试的思路
3. **Review**：你贴关键代码，导师做逐段 review（正确性、契约一致性、隐患）
4. **验收**：自查清单 + 该子任务的可观测结果（curl / 前端页面 / 测试）
